# ID Generation Strategy - Production Grade

## Overview

This application uses **application-generated IDs** instead of database auto-increment for all domain entities. This approach follows enterprise best practices and provides significant advantages for distributed systems.

## Snowflake Algorithm

We implement the **Snowflake ID generation algorithm**, originally developed by Twitter for distributed ID generation at scale.

### ID Structure (64-bit Long)

```
┌─────────────────────────────────────────────────────────────────┐
│                        64-bit Snowflake ID                      │
├──┬──────────────────────────────┬────────────┬─────────────────┤
│1 │         41 bits              │  10 bits   │    12 bits      │
│  │       Timestamp              │  Worker ID │   Sequence      │
│0 │    (milliseconds)            │  (0-1023)  │   (0-4095)      │
└──┴──────────────────────────────┴────────────┴─────────────────┘
```

### Breakdown:

1. **1 bit**: Unused (always 0)
2. **41 bits**: Timestamp in milliseconds since custom epoch (2024-01-01)
   - Supports ~69 years from custom epoch
3. **10 bits**: Worker/Machine ID (0-1023)
   - Supports up to 1024 different workers/servers
4. **12 bits**: Sequence number (0-4095)
   - Supports 4096 IDs per millisecond per worker

## Key Features

### ✅ Time-Ordered (Sortable)
- IDs are naturally sorted by creation time
- Newer records have larger IDs
- Database indexes remain efficient (no fragmentation)
- Range queries work naturally: `WHERE id > X`

### ✅ Globally Unique
- Combination of timestamp + worker ID + sequence ensures uniqueness
- No coordination between servers needed
- No database roundtrip required

### ✅ High Performance
- **Millions of IDs per second** per worker
- 4096 IDs per millisecond per worker
- Zero network calls (fully local)
- Zero database queries for ID generation

### ✅ Distributed-Friendly
- Each server/worker has unique worker ID
- No single point of failure
- No central coordinator needed
- Scales horizontally

### ✅ Production-Ready
- Battle-tested algorithm (used by Twitter, Discord, Instagram)
- Thread-safe implementation
- Handles clock drift gracefully
- Prevents duplicate IDs even during high load

### Usage Example

```kotlin
@Service
class ExpenseWriteServiceImpl(
    private val idGenerator: IdGenerator
) {
    fun createExpense(command: CreateExpenseCommand): Mono<Expense> {
        val expenseId = idGenerator.generate()

        val expense = Expense(
            expenseId = expenseId,  // Application-generated ID
            userId = command.userId,
            amount = command.amount,
            ...
        )

        return expenseRepository.save(expense)
    }
}
```

### Configuration

**Worker ID** can be set via environment variable:

```bash
# Production - set unique ID for each server
export WORKER_ID=1  # Server 1
export WORKER_ID=2  # Server 2
...

# Kubernetes - use pod ordinal
export WORKER_ID=$(hostname | grep -o '[0-9]*$')
```

If not set, worker ID is derived from system time (suitable for development).

## Entity Naming Convention

### Domain Model Field Names
- Use meaningful domain names in entities
- Examples:
  - `expenseId` for Expense entity
  - `approvalId` for Approval entity
  - `userId` for User entity

### Database Column Name
- All ID columns are named `record_id` in the database
- Provides consistency across all tables
- Uses Spring Data `@Column` mapping

```kotlin
@Table("expenses")
data class Expense(
    @Id
    @Column("record_id")  // Maps to database column
    val expenseId: Long,  // Domain model field name
    ...
)
```

### Database Schema

```sql
CREATE TABLE expenses (
    record_id BIGINT PRIMARY KEY,        -- Application-generated
    user_id BIGINT NOT NULL,
    amount NUMERIC(14, 2) NOT NULL,
    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL
);

CREATE TABLE approvals (
    record_id BIGINT PRIMARY KEY,        -- Application-generated
    expense_id BIGINT NOT NULL REFERENCES expenses(record_id),
    approver_id BIGINT NOT NULL,
    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL
);
```

**Note**: No `SERIAL` or `BIGSERIAL` - IDs are generated by application.

## Advantages Over Database Auto-Increment

| Feature | Snowflake IDs | DB Auto-Increment |
|---------|--------------|-------------------|
| **Performance** | No DB roundtrip | Requires DB query |
| **Distributed** | ✅ Works across servers | ❌ Single DB constraint |
| **Sortability** | ✅ Time-ordered | ❌ Random order (UUID) |
| **Uniqueness** | ✅ Globally unique | ⚠️ Per table |
| **Scalability** | ✅ Infinite horizontal | ❌ Limited by DB |
| **Offline Mode** | ✅ Can generate offline | ❌ Requires DB connection |
| **Sharding** | ✅ Shard-friendly | ❌ Complex coordination |
| **Migration** | ✅ Easy to migrate data | ❌ ID conflicts |

IDs encode useful metadata:
- **Timestamp**: When was this entity created?
- **Worker ID**: Which server created this entity?
- **Sequence**: How many entities were created in that millisecond?

This is invaluable for:
- Debugging distributed systems
- Performance monitoring
- Identifying hot spots
- Troubleshooting data issues

## Migration Guide

If you have existing entities using database auto-increment:

### 1. Update Entity

```kotlin
// Before
@Table("expenses")
data class Expense(
    @Id val id: Long? = null,  // ❌ Nullable, auto-generated
    ...
)

// After
@Table("expenses")
data class Expense(
    @Id
    @Column("record_id")
    val expenseId: Long,  // ✅ Non-null, application-generated
    ...
)
```

### 2. Update Database Schema

```sql
-- Rename column
ALTER TABLE expenses RENAME COLUMN id TO record_id;

-- Remove auto-increment (PostgreSQL)
ALTER TABLE expenses ALTER COLUMN record_id DROP DEFAULT;
DROP SEQUENCE IF EXISTS expenses_id_seq;
```

### 3. Update Service

```kotlin
@Service
class ExpenseService(
    private val idGenerator: IdGenerator  // Inject ID generator
) {
    fun createExpense(command: CreateExpenseCommand): Mono<Expense> {
        val expense = Expense(
            expenseId = idGenerator.generate(),  // Generate ID
            ...
        )
        return repository.save(expense)
    }
}
```

## Best Practices

### ✅ DO

- Generate IDs in the application layer (service/use case)
- Use meaningful field names in domain entities (`expenseId`, not `id`)
- Map to consistent database column names (`record_id`)
- Set `created_at` and `updated_at` in application code
- Configure unique worker IDs in production
- Log worker ID on application startup

### ❌ DON'T

- Don't rely on database for ID generation
- Don't use nullable ID fields (`Long?`) in domain entities
- Don't check for null IDs - they should always be present
- Don't forget to inject `IdGenerator` in services
- Don't use the same worker ID for multiple servers

## Troubleshooting

### Clock Moved Backwards

**Error**: `Clock moved backwards by X ms`

**Cause**: System clock was adjusted backwards

**Solution**:
- Use NTP to keep clocks synchronized
- Don't manually adjust system time on production servers
- The generator will wait for clock to catch up

### Duplicate Worker IDs

**Symptom**: Potential ID collisions in distributed environment

**Solution**:
- Ensure each server has unique `WORKER_ID`
- Use orchestration tools to assign unique IDs
- Monitor worker IDs in application logs

### Sequence Exhausted

**Symptom**: Application pauses briefly during high load

**Cause**: Generated 4096 IDs in single millisecond

**Solution**: This is handled automatically - generator waits for next millisecond
